# 三次提交的 IB 记录：94 TiB 不在任何一次 IB 里

`plug1` 轮次（新插件、新 Turnip，`tmp/boot-plug1.img`）的持久日志
`build/sheng-logs/plug1-0000001275249335/latest.txt` 里有驱动自己的 IB 记录
（`BootLog.c:551-562`，取自 `NativeAdrenoSubmit.cpp:313-318` 的 `native_adreno_ib_log`）。

## 三次提交

| fence | `iova` | bytes | 谁 |
| --- | --- | --- | --- |
| 5 | `0x020004000` | 48 | 内核自测的第一次 |
| 6 | `0x020004000` | 48 | 内核自测的第二次 |
| **7** | **`0x100027000`** | **736** | **用户态（Metal 的第一笔）** |

`0x100027000` = 4 GiB + 0x27000，正好在 `GpuClientVaStart = 0x100000000`（4 GiB）之上。
与 `NativeAdrenoPublish.cpp:116-120` 的窗口定义一致：**用户连接的地址从 4 GiB 起。**

## 94 TiB 不在任何一次 IB 里

故障地址是 `far = 0x5e09e55794f5`（94.0 TiB）。三次 IB 的地址是
`0x020004000`（512 MiB + 16 KiB）与 `0x100027000`（4 GiB + 156 KiB），
**两者都不在 94 TiB 附近，差六个数量级。**

所以 `far` 不是「IB 的首地址」，也不是「IB 被放错了地方」。

## fence 7 的 IB 头 28 个字全是 0

```
[ib] fence=7 iova=100027000 bytes=736
I00 00000000 00000000 00000000 00000000 00000000 00000000 00000000 00000000
I08 00000000 00000000 00000000 00000000 00000000 00000000 00000000 00000000
I10 00000000 00000000 00000000 00000000 00000000 00000000 00000000 00000000
I18 00000000 00000000 00000000 00000000
```

这 28 个字由 `vm_->peekWords(buffers[0].iova, head, 28)` 读出（`NativeAdrenoSubmit.cpp:314`），
在 `publishMapped()` **之后**（`:315` 在 `:293` 之后）。所以它读的是已发布的映射。

**一个 736 字节的 IB，开头 28 个字全 0，有两种解释：**

1. **CPU 读到的就是 0**：Metal 还没写 IB 的内容就提交了（或者写到别的地方）；
2. **读路径有问题**：`peekWords` 读的是 write-combined 映射，CPU 的写还在缓冲区里。

**判据**：`native_adreno_coherence[4]`（`distrustWriteCombined` 触发计数）如果非 0，
说明驱动自己已经发现过「写入没到内存」；如果为 0，说明驱动认为内存是一致的，
那么解释 1 成立——**IB 内容真的是 0**。

下一轮读这个计数就能分开。

## 与 `GPUROW28` 的关系

`GPUROW25` 的 `sub 3/2` 说明第三次提交永不完成，而它的 IB 头是 0。
**一个全 0 的 IB 被 CP 执行时，第一个字 `0x00000000` 不是合法 PM4 命令**——CP 可能
按 `type 0` 解释（`a6xx` 的 `CP_NOP` 是 `0x10000000`，`0` 不是），于是跳到别处或读错地址。

**这与 `far = 94 TiB` 一致**：CP 从一个无效 IB 里取到了垃圾，然后按它去访问。

**这条把故障从「SMMU 配置」移到了「IB 内容」**，而 IB 内容由 Metal（用户态）写。

## 决定性数据：ring 里的 IB 地址被截断到 32 位

`coh1` 轮次（`86a0262` 的 `BootLog.c` 加了 `[coherence]` 行与 per-IB 的 `wc-` 标记）
的持久日志 `build/sheng-logs/coh1-0000000322ba32e4/latest.txt`：

```
[ib] fence=7 iova=100027000 bytes=736 wc-trusted
[ib] fence=6 iova=020004000 bytes=48 wc-trusted
[ib] fence=5 iova=020004000 bytes=48 wc-trusted
[coherence] samples=1 cached=ffffffff before=ffffffff after=ffffffff distrust=0 first 00000000/00000000/00000000
```

```
[ring] fence=7 ring 4e..5f words=17
R000 70460001 00000031 70460001 00000018 70460001 00000019 70bf8003 00027000
R008 00000001 000000b8 48088501 00000007 70460004 80000004 00300004 00000000
R010 00000007
```

### 两条读数的对照

| 量 | 驱动记的（`[ib]`） | ring 里实际写的（`[ring]`） |
| --- | --- | --- |
| IB 地址 | `0x100027000` | **`0x00027000`** |
| IB 长度 | 736 bytes | **`0xb8` dwords = 736 bytes**（一致） |

**长度一致、地址少了高位 `0x1`。** `0x100027000` 与 `0x00027000` 差的正是 4 GiB
（`GpuClientVaStart = 0x100000000`）。

### `wc-trusted` 与 `distrust=0` 排除了「缓存没刷」

驱动从未发现过 write-combined 写入没到内存（`distrust=0`），且 `[coherence]` 的
`cached == before == after == ffffffff` 说明那次采样读到的内存是一致的。
**所以 `[ib]` 里那 736 字节全 0 是真的——驱动按 `0x100027000` 读，读到的就是 0，
因为 Metal 把 IB 写在了 `0x27000`。**

### 谁是 0x70bf8003

`0x70bf8003` 的 type 7、opcode **`0xbf`**。驱动自己的 `SubmitIndirectBuffer` 是 **`0x3f`**
（`NativeAdrenoSubmit.cpp:9`），所以这个字**不是驱动生成的**——它来自用户态
（Metal / Turnip）写进 ring 的命令流。

**所以：Turnip 在构造 `CP_INDIRECT_BUFFER` 时把 4 GiB 的基址丢了。**

### 后果链

1. Turnip 把 IB 地址写成 `0x27000`（32 位截断）；
2. 驱动按 `0x100027000` 记录并校验（通过，因为那个地址确实映射了）；
3. CP 按 ring 里的 `0x27000` 去读——那是另一个地址，读到的是别的东西；
4. `far = 0x5e09e*` 是 CP 从那块错地方取到的垃圾，SMMU 报 UCHE OOB；
5. 第三次提交永不完成（`sub 3/2`）。

### 下一轮（离线可做）

在 `tmp/parity-src` 与 Turnip 的 darwin 后端里查 `CP_INDIRECT_BUFFER` 的构造：
地址是怎么拼的、有没有把 `GpuClientVaStart` 加回去。**这是用户态侧，不是 SMMU 配置。**

**判据**：Turnip 写进 ring 的地址应当等于 `buffer.iova`（`0x100027000`）。
现在它少 4 GiB。

## 更正：ring 里的地址没有截断，我读错了

上面「地址被截断到 32 位」是错的。`NativeAdrenoSubmit.cpp:225-227` 写的是三个字：

```cpp
words[word_count++] = (uint32_t)buffer.iova;        // 低 32 位
words[word_count++] = (uint32_t)(buffer.iova>>32);  // 高 32 位
words[word_count++] = (uint32_t)(buffer.bytes/4);   // 长度（dwords）
```

ring 里是：

```
70bf8003 00027000 00000001 000000b8
```

| 字 | 值 | 含义 |
| --- | --- | --- |
| `0x00027000` | `0x100027000 & 0xffffffff` | **低 32 位** |
| `0x00000001` | `0x100027000 >> 32` | **高 32 位** |
| `0x000000b8` | `736 / 4` | 长度，dwords |

**三个字完全正确：地址 = `0x00000001_00027000` = `0x100027000`，长度 736 字节。**

我把「低、高」两字读成了「地址、长度」，于是以为地址少了高位。

## 更正后的结论

- **ring 里的地址是对的**（`0x100027000`，与 `[ib]` 一致）；
- **`[ib]` 读到那 736 字节全 0 是真的**：驱动按正确地址读，读到 0；
- `wc-trusted` + `distrust=0` + `cached==before==after` 排除了「写入没到内存」。

**所以：Metal 提交了一个 736 字节的 IB，那个地址在 GPU 地址空间里映射着，但内容是 0。**

## 剩下的两种解释

1. **Metal 没写 IB 内容就提交**（它的 `NativeAdrenoAbiSubmitBuffer.iova` 指向一块它以为写了、
   实际没写的内存）；
2. **驱动读的那块内存与 Metal 写的那块不是同一块**——映射存在，但两张表指向不同的物理页
   （这正是 `reference.md §36.3` 与 `§31` 记的窗口/别名一族的问题）。

**分开它们的判据**：读 `vm_->describe(buffer.handle, &iova, &bytes, &permissions)` 的返回值
与 `buffer.iova` 的差——若 `buffer.iova == iova`（映射起点相同）而内容仍是 0，
解释 1；若 `buffer.iova != iova`（在映射内部偏移），则要核那个偏移指向的物理页。

`[ib]` 行已经在记 `iova`（`buffer.iova`），但没记 `describe` 给的映射起点。
**下一轮加这一个数就能分开。**

## 补：读 IB 用的是这次提交自己的 VM

`NativeAdrenoSubmit.cpp:198` 有一行局部遮蔽：

```cpp
NativeAdrenoVm *const vm_=vm;   /* this submission's VM: every vm_ below is the job's own */
```

所以 `:314` 的 `vm_->peekWords(buffers[0].iova, head, 28)` 读的是**这次提交的 VM**，
不是内核的。用户态的第三次提交读的就是它自己的 `NativeAdrenoProcessVm`。

**且 `:214-216` 的校验已经证明这个地址属于该 VM 的一个映射**：

```cpp
if(!(permissions&ArmSmmu4KRead) || buffer.iova<iova ||
    buffer.iova-iova>bytes || buffer.bytes>bytes-(buffer.iova-iova))return kIOReturnBadArgument;
```

`buffer.iova = 0x100027000`、`buffer.bytes = 736` 通过了这一条，所以
`describe(handle)` 给的映射起点 `iova` 与长度 `bytes` 覆盖了它。

**结论不变：地址对、映射在、内容 0。**

## 这意味着什么

要再往前一步，只有两个方向：

1. **在驱动里记 `describe` 给的映射起点**（`iova`）与 `buffer.iova` 的差。若差非 0，
   IB 是从映射内部某个偏移开始的——那要核那个偏移在 Metal 的布局里是什么。
   **这要改 `native_adreno_ib_log` 的布局（4 个槽 × 32 字已满），是一次驱动改动。**
2. **在 Turnip 的 darwin 后端记每次 `submit_create` 的 buffer 内容**——那是
   `tu_knl_darwin.cc` 的 `darwin_queue_submit`，改的是 `tmp/parity-src` 之外的
   mesa 补丁，代价更大。

**两条都不是「读一个已有的数」能做到的。** 所以 `docs/evidence/2026-10-31-uche-fault.md`
那条「加一个数就能分开」的判据**估计得太乐观**——数组没有空位，要扩布局。
