## Link result

The full PARF alignment and the pipe-clock vote changed the first DBI access from a hang to a
returning read:

```
PCIE 11: about to read dbi dbi gen3_gen2_ctrl before at 0xfffffff1d4e8a80c
PCIE 11: dbi dbi gen3_gen2_ctrl before (...) = 0x20190
PCIE 11: about to write dbi dbi gen3_gen2_ctrl (0x1f00 = 1) ...
PCIE 11: the link after 0 ms: elbi 0x1 dll 0x10110008 id 0x10b17cb
PCIE 11: the link after 5 ms: elbi 0x11401 dll 0x30120008 id 0x10b17cb
PCIE 11: THE LINK IS UP after 5 ms (endpoint 0x17cb:0x10b)
PCIE 11: step 11: done
PCIE 12: steps done; the controller is left as it was found
```

This is a real link-up reading: ELBI bit 10 set, DBI 0x80 bit 29 set, and the endpoint answers
`17cb:10b` (QCA6390). It is not yet a Wi-Fi result: no BAR setup, DMA, MSI, firmware, MHI, QMI,
QRTR or scan/join exists in this tree.

## Why the boot still does not reach the desktop

- `DATAMOUNT stage=0 status=-1 ro=-1 store=0`; the good desktop round `wl1600071` has
  `stage=4 status=0 ro=0 store=2`.
- `[addon] 1=0/-1 2=0/-1 3=0/-1`; all three addon mounts stay at zero because
  `native_gpu_addon_prepare()` runs only after Data reaches stage 4.
- `SUPER ... own=0 sw=0/0/0`, `PROC s=0`, `tf=71` frozen.
- `CORES` changes from `deaf=00` at t=10 s to `deaf=1e` at t=30 s; c4's counters freeze after
  the link is up. The link-up event is followed by a core losing timer interrupts.

The current probe has no PCIe interrupt owner. The vendor masks all PARF interrupts before link
training (`pci-msm.c:4537-4552`); the local probe did not. Source revision `e3d5a6f` now adds
`PARF_INT_ALL_MASK=0` and `PARF_INT_ALL_CLEAR=0xffffffff` before link training. A normal control
image without `pcie=` (`tmp/boot-norm1.img`) is built to separate a probe-induced stall from the
known random one. pc5 (the same probe plus the mask) is built at `tmp/boot-pc5.img`, sha256
`f6226e275bb2f645840e58758f2a792515b6c50da1fa9faf1fa32020f24c6ef3`; neither pc5 nor norm1 has a
board result yet.
