# 第一次写 PMIC：三条命令发了，投票没有完成

2026-10-31 13:52 的 `rail2` 轮次（`tmp/boot-rail2.img`，`pcie=13 pcie_skip=32 pcie_rail=2`，
`sheng-build-tag=rail2`）。**这是这个移植第一次对 PMIC 电源轨发起写操作。**

## 读数（`tmp/console-rail2.log`，逐字）

```
PCIE 12: step 13 is read only; no rail has been voted
PCIE 13: the first write this file makes to a power rail: ldoa5 (pm8150_l5, 0.9 V) through RPMh
PCIE 13: command 1: address 0x41800, data 880 (voltage 880 mV)
PCIE 13: command 2: address 0x41804, data 1 (enable 1)
PCIE 13: command 3: address 0x41808, data 7 (mode 7 (pmic5-ldo HPM))
PCIE 13: the RSC DRV 2 config reads 0x800c8104: 8 TCS, 16 commands each
PCIE 13: using TCS 0 (status 0x1)
PCIE 13: the vote DID NOT COMPLETE after 2000 polls; command status 0x10101
```

## 能确立的

| 事实 | 证据 |
| --- | --- |
| 三个命令的值正确 | `0x41800:880`、`0x41804:1`、`0x41808:7`，与 `progress/2026-10-31.md §5.4` 的表一致 |
| 命令确实被写入 TCS | 它们出现在日志里，且 `TCS_CMD_STATUS` 有非 0 值 |
| RSC DRV 2 可读、配置合理 | `0x800c8104`：8 个 TCS、每 TCS 16 条命令 |
| **投票没有完成** | 2000 次轮询（每次 5 µs，共 10 ms）后 `RSC_DRV_IRQ_STATUS` 的完成位仍未置 |
| **命令状态不是 Linux 定义的两个位** | `0x10101` 的三个字节各 `0x01` = `BIT(0)`；Linux 判的是 `CMD_STATUS_ISSUED` = `BIT(8)` 与 `CMD_STATUS_COMPL` = `BIT(16)`（`reference/k40-kernel/drivers/soc/qcom/rpmh-rsc.c:64-65`） |

## 不能确立的

**「`0x01` 表示 RPMh 拒绝」只是推断，不是事实。** vendor 驱动里没有 `BIT(0)` 的定义；
Linux 的 `rpmh-rsc.c` 只检查 `BIT(8)` 与 `BIT(16)`，遇到 `0x01` 会走
`Incomplete request` 分支并报 `-EIO`（`:283-289`）——**那是「没完成」，不是「被拒绝」**。

**也不能说轨没开**：`0x60000000` 那一步这一轮没跑到（`step 13` 在投票后停下）。

## 下一轮该问的（离线先做）

1. **`0x01` 是什么**：在 `reference/k40-kernel` 里搜 `RSC_DRV_CMD_STATUS` 的所有用法，
   以及 vendor 的 `rpmh-rsc` 有没有第三个状态位（`BIT(0)`）。若有，它的名字决定下一步。
2. **为什么 IRQ 不置**：`RSC_DRV_IRQ_STATUS` 的完成位依赖 TCS 的 `AMC` 模式与 trigger 序列
   （`alioth_pcie.c:1255-1259` 的四次 `RSC_W`）。Linux 的做法是 `TCS_AMC_MODE_ENABLE` +
   `TCS_AMC_MODE_TRIGGER`（`rpmh-rsc.c:56-57`）；**对照那四次写与 Linux 的 `rpmh_rsc_write_ctrl_data`
   是否等价。**
3. **`pcie=13` 这一轮没跑到 `0x60000000` 的读**：要判轨状态，得让 `pcie` 更大，或把读放在投票之后。

## 这一轮的边界

**没有写坏硬件**：三条命令都是正确值（880 mV / enable / HPM），即使 RPMh 接受了也是安全的。
**也没有证据说它被接受了**——投票没完成，`0x60000000` 没读。

**不要重试第二次写入**：同样的值再写一次无害，但重试会掩盖第一次的读数，而第一次才是判据。

## 一处不一致：持久日志的 tag 是 `usb190`，镜像是 `rail2`

```
strings tmp/boot-rail2.img | grep sheng-build-tag   → sheng-build-tag=rail2
build/sheng-logs/usb190-0000000015b48d6e/header.txt → tag usb190, boot_id 0x15b48d6e, uptime_s 120
```

那个目录的 mtime 是 13:53（本轮），`boot_id` 是新的，**所以它确实是这一轮写的**，
只是 `tag` 字段是 `usb190`。

**`tmp/boot-usb190.img` 不存在**，`board.toml` 里也没有 `usb190`，
`build_tag` 是 `static char[32]` 默认空（`BootProgress.c:95`）。

**不能确立原因。** 两种可能：
1. 写线程启动时 `sheng-build-tag` 还没进 boot args（`PE_parse_boot_argn` 的时机）；
2. `tag` 字段在某个早于 `PE_parse_boot_argn` 的路径上被填了别的值。

**这条与 `m7`/`m12`、`pcie_rail=2` 的「镜像里 A、运行时 B」是同一族，但这一条不影响
本次结论**——投票的三条命令与 `0x10101` 都来自 console，不依赖 `tag`。

**判据**：下一轮先 `grep -a 'sheng-build-tag' tmp/console-<tag>.log`，看运行时解析到几。
