# 失聪的是一颗线程，不是一颗核

2026-11-06 傍晚。设备仓库 `NEW/UniXNU-alioth`，ArmCpu `9750897`，`GICR` 行新增
`ac=<线程 id>/<state>`（`cpu_datap(core)->cpu_active_thread`）。真机读数，USB 串口抓取，
`fastboot boot`，不写槽。

| 镜像 | 与上一镜像的差别 | 原始抓取 |
| --- | --- | --- |
| `boot-w9.img` | `GICR` 行加 `ac=` | `tmp/console-w91324111.txt`、`tmp/console-w91331332.txt` |

## 1. 两轮，同一颗线程，不同一颗核

```
w91324111  t=190s deaf=20 c5=500/8040000/80000ff/0/0 ac=6f/4
w91331332  t=170s deaf=18 c4=400/8040000/80000ff/0/0 ac=6f/4
```

两轮的活动线程都是 `0x6f`（tid 111），状态都是 4 = `TH_RUN`。定时器 PPI 在两轮里
都是 **pending + 使能 + 从未 active + `WAKER` 0**。封住的是 c5，还是 c4，随轮次变；封住的是
谁，不变。

## 2. 计数冻结的精确时刻

```
w91324111  c5=12155/1100   从 t=20s 到 t=190s 一字未变
w91331332  c4=191714/6874  从 t=20s 到 t=170s 一字未变
```

`wd=` 之后的掩码是**正式判定**（连续三次采样不动），`CORES`/`GICR` 行里的 `deaf=` 只是
"疑似"（连续两次）。第二轮 t=170s 时 `wd=3/1c`：c2、c3、c4 都被正式判过一次，但 c2、c3 的
计数在动（t=80s 11228 → t=170s 11263），c4 不动。**慢不是死。**

## 3. 疑似核上是 idle 线程

t=30s 的 `GICR` 行同时给出疑似核：

```
c1=100/40000/80000ff/0/0 ac=ce/84   0x84 = TH_RUN|TH_IDLE
c2=200/40000/80000ff/0/0 ac=d0/84
c3=300/40000/80000ff/0/0 ac=d2/84
c4=400/8040000/80000ff/0/0 ac=6f/4   state 4 = TH_RUN（无 TH_IDLE）
```

疑似核的 `ISPENDR0` 是 `40000`，不是定时器；它们的活动线程是 idle 线程，并且下一轮采样就
恢复。**只有 state 恰为 4 的那颗核永久停摆。**

## 4. 这修正了上一份证据的结论

`2026-11-06-deaf-core-gic-state.md` 把"睡在该核上的线程永远不醒"当作根因。w9 的 `ac=` 把顺序
倒过来：**根因是这颗核正在跑一个真实线程、并且不取中断**（`ISACTIVER0=0` 表示 CPU 从未应答，
所以 GIC 一直显示 pending）；睡在该核上的线程醒不来，是这个状态的**后果**。

第二轮同时否掉了"触控线程"这一假设：`tf` 从 2834 一路爬到 11715，`tc=6`，触控正常，而 c4
照样失聪。第一轮 `tf` 冻在 838，只是触控线程恰好睡在 c5 的定时器队列上。

## 边界

- tid 111 的身份未定。`boot-w10.img` 在同一行加 `nm=<进程名>`（`proc_name(task_pid(...))`）
  与 `k=<continuation 地址>`，用来判定它卡在内核哪个例程。
- 相位字段 `ph`/`age` 在全部轮次、全部核上恒为 `ph0 age0s`，包括计数正在涨的核。它们现在
  不区分"不在中断处理程序里"与"符号未解析"，不能当证据用。
