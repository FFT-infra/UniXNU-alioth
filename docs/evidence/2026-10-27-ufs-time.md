# UFS root-verification timing, measured on the phone

The `UFS TIME` row in `package/BootProgress.c` is the only record of where root
verification time goes: `verify_ms` is the in-kernel SHA-256, `read_ms` is the
UFS transfer. It was drawn on the panel only, so every reading so far was taken
by hand and none was kept. boot-usb40 sends it to the USB console; boot-usb41
samples it every 10 s, which is what dates the work.

## What the row does not mean

`other = t - (verify_ms + read_ms)` is uptime that is **not inside a UFS
command**. It is not CPU work and not a cost. A final total therefore cannot say
whether UFS delayed the desktop; only the series can.

## Three phases, three different problems

**1. t5-t65, the root verification read: already near the window cap.**
27-28 blocks per command (108-114 KiB) against `kDataMax` of 131072 bytes
(32 blocks, 128 KiB) in `RootTransportLayout.h`, so 84-88% of the driver's own
window. 2831 MiB in 22.9 s = **123 MiB/s**. Raising the per-request size here
buys almost nothing; the driver is already filling its window.

**2. The same command size runs 6x faster later in that phase.**
t5-t35 costs 1990 us per command (57 MiB/s); t35-t65 costs 331 us (341 MiB/s).
The commands are the same 113 KiB. The 1659 us difference is **two blocked
timer ticks, not transfer time**: `IODelay(1)` calls `delay_for_interval`, which
spins only when `ml_delay_should_spin` sees the interval below the CPU's idle
latency. That latency comes from the ADT `powergate-latency` property, this
board's device tree does not carry it, so it stays 0 and **every `IODelay`
blocks the thread until the next tick, ~830 us**. Late in the phase the command
is already complete on the first check and no delay is taken; early it is not.
boot-usb42 spins on the doorbell register for a bounded window first.

**3. t65-t105, the userspace metadata reads: genuinely fragmented.**
1.3-2.2 blocks per command (5-9 KiB), 384 MiB in 23.4 s = **16.4 MiB/s**. At the
123 MiB/s the big-command phase reaches, the same bytes take 3.1 s, so about
**20 s is recoverable here** — and unlike phase 1 this is real headroom.

## What this means for the desktop

The lock screen appears at roughly 104 s. At t105 UFS had spent 54.0 s, which is
51% of the uptime to that point, so the transport is on the critical path. Of
that 54 s:

- **23 s is already near optimal** (phase 1, 123 MiB/s, window 85% full).
- **23 s is fragmented** (phase 3, 16.4 MiB/s) with about 20 s recoverable.
- 7 s is the SHA-256 (10% of the two), so corecrypto assembly is worth ~7 s.

After t105 the `read` counter keeps climbing to 112 s by t715. That 65 s is
background read-ahead after the desktop is already up, and it does not delay the
desktop.

## Rejected, with the reason

- **Rebuilding corecrypto with `CC_USE_ASM=1`.** Worth ~7 s. `scripts/
  build-corecrypto-14.py:80` sets `-DCC_USE_ASM=0` in `origin/main`, and enabling
  it needs the corecrypto `.s` files this build never compiles plus
  `AccelerateCrypto_SHA256_compress_arm64neon`, which XNU does not provide. A
  local divergence from upstream for a small gain.
- **"27 万次 15 KB 小请求，扩到 128 KB 可省 50 秒".** The 15.7 KB figure is an
  average over two phases with different behaviour. Phase 1 is already at
  113 KiB per command; the fragmentation is phase 3, and its ceiling is ~20 s.
